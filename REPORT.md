## I. Problem Definition & Domain Research

### The "Why": The Real-World Problem

Software engineering teams routinely inherit large, undocumented, or unfamiliar codebases. A junior developer joining a team with hundreds of thousands of lines of code across dozens of modules faces a steep onboarding curve. Searching for "where authentication is handled" or "how the database connection is initialized" requires either reading through files manually or relying on tribal knowledge that may not exist.

Existing tools like GitHub's search or IDE-based text search are purely lexical — they match exact keywords. A developer asking *"how does this system handle session expiry?"* will find nothing if the code uses variable names like `token_timeout` or `refresh_window`. The vocabulary gap between how a human frames a question and how code is written makes traditional search fundamentally limited.

**Our project solves this problem using Retrieval-Augmented Generation (RAG):** a pipeline that first retrieves the most semantically relevant code chunks using vector similarity, then feeds them to a Large Language Model (LLM) for a natural-language explanation. The core challenge is the quality of retrieval — a generic sentence embedding model trained on natural language has never seen code and performs poorly on the code-to-question similarity task.

**The primary machine learning objective of this project is therefore: fine-tune a dense retrieval embedding model so that it learns to map developer questions and code snippets into a shared semantic vector space.** This allows a query like *"how are workers dispatched concurrently?"* to retrieve a Go goroutine snippet, even if no word from the question appears in the code.

### Data Provenance: Where Did the Data Come From?

Since no large, publicly available, labeled dataset of (question, code snippet) pairs existed for our specific multi-language, multi-domain use case, we **synthetically generated our own training dataset** using the Groq API with `llama-3.1-8b-instant`.

**Script:** `training/generate_dataset.py`
**Output:** `training/training_data.jsonl` (550 labeled pairs)

**Generation Strategy:**
The generator was given 18 deliberately diverse programming domains:
- Python (Pandas Data Science, Django Backend)
- JavaScript/TypeScript (React, Node Express)
- Go (Microservices, Concurrent Workers)
- Java (Spring Boot, Database Entities)
- C/C++ (Memory Management, Game Engine)
- Rust, Ruby on Rails, PHP Laravel, C# .NET, SQL Analytics, Shell/CI-CD, Docker

For each topic, the LLM was prompted to generate 4 realistic code snippets accompanied by a natural language question a developer would ask to find that code. This process was repeated with random topic selection until 550 pairs were collected.

**Dataset Features:**
| Feature | Description |
|---|---|
| `question` | Natural language question a developer might ask |
| `code` | Realistic source code snippet that answers that question |
| `file_path` | Simulated file path (e.g., `database/connection.go`) |
| `language` | Programming language of the snippet |

**Missing Values:** Entries with missing `question` or `code` fields were rejected at generation time by the validation check `if "question" in entry and "code" in entry`. No missing values exist in the final dataset.

**Potential Biases:**
1. **LLM-generated data bias:** The data was generated by `llama-3.1-8b-instant`. This means the model's own stylistic patterns, naming conventions, and code structure preferences are baked into the training set. Real-world codebases written by humans may differ significantly in style.
2. **Topic imbalance:** Topics were sampled randomly with uniform probability, but some topics generate more distinct code patterns than others. For example, Python and JavaScript patterns are more varied and well-represented in the LLM's training data than Rust or Kotlin patterns.
3. **Vocabulary bias toward common patterns:** The LLM tends to generate "textbook" code rather than the convoluted, legacy code a developer actually encounters in the wild. The model may perform worse on real codebases with unusual architecture patterns.
4. **English-only questions:** All generated questions are in English. The model will not generalize to non-English developer queries.

## II. Methodology & Design Choices

### Preprocessing Logic

**Step 1: Source Code Chunking**
Raw source files cannot be passed directly to the embedding model — they are too large (the model has a 256-token input limit). The `backend/chunker.py` module splits each file into fixed-size chunks of 200 lines:

```python
def chunk_code(text, file_path="unknown", language="unknown", chunk_size=200):
    lines = text.split("\n")
    for i in range(0, len(lines), chunk_size):
        chunk_lines = lines[i:i + chunk_size]
        chunks.append({
            "code": "\n".join(chunk_lines),
            "file_path": file_path,
            "language": language,
            "start_line": i + 1,
            "end_line": min(i + chunk_size, len(lines)),
        })
```

**Why fixed line-based chunking over token-based or AST-based chunking?**
- **AST-based chunking** (splitting at function or class boundaries) would be ideal semantically but requires a parser for each language, creating significant implementation complexity across 15 supported languages.
- **Token-based chunking** is model-specific and harder to reason about from a developer's perspective (line numbers are more meaningful to users).
- **Fixed-line chunking** is simple, language-agnostic, and predictable. 200 lines was chosen as a balance between giving the model enough context to understand a code block while staying within the embedding model's effective range.

**Step 2: Dataset Cleaning**
Before training, the `training_data.jsonl` file was loaded and any entry lacking the required `question` or `code` keys was discarded. No normalization (lowercasing, stemming) was applied to either questions or code — unlike NLP tasks, code is case-sensitive and tokenization must preserve structure. Whitespace was not stripped because indentation is syntactically meaningful in Python and significant in other languages.

**Step 3: Train/Validation/Test Split**
The 550-pair dataset was split using `sklearn.model_selection.train_test_split` with `random_state=42` for reproducibility:
- **80% Training** (≈440 pairs): Used to update model weights via gradient descent
- **10% Validation** (≈55 pairs): Used to evaluate the model during training and detect overfitting
- **10% Test** (≈55 pairs): Held out entirely and never used during training or model selection

```python
df_train, df_temp = train_test_split(df, test_size=0.2, random_state=42)
df_val, df_test = train_test_split(df_temp, test_size=0.5, random_state=42)
```

### Architecture Selection: Why `all-MiniLM-L6-v2`?

The central model being fine-tuned is `all-MiniLM-L6-v2`, a **Sentence Transformer** — a bi-encoder architecture that encodes each input independently into a fixed-size dense vector (embedding). Similarity between a question and a code snippet is then computed as the cosine or L2 distance between their respective embeddings.

**Why this model over alternatives?**

| Alternative | Reason Rejected |
|---|---|
| **Large LLM (GPT-4, Llama-70B) as retriever** | These models are too large to embed thousands of code chunks efficiently. A 70B model would take minutes per query for embedding. |
| **BM25 (keyword-based retrieval)** | Purely lexical. Cannot bridge the vocabulary gap between natural language questions and code. |
| **Cross-encoder reranker** | Cross-encoders compare each (query, document) pair jointly, giving better accuracy but requiring O(n) forward passes at query time — too slow for real-time use. |
| **CodeBERT / UniXcoder** | More specialized code models exist, but they are significantly larger, slower, and harder to fine-tune with limited data. |
| **`all-mpnet-base-v2`** | Better baseline accuracy but 4x slower inference with only marginal gains for our use case. |

`all-MiniLM-L6-v2` was chosen because:
1. It is lightweight (22M parameters), enabling fast embedding at inference time
2. It has a strong baseline for semantic similarity tasks
3. It is natively supported by the `sentence-transformers` library, simplifying training
4. Its 384-dimensional output fits efficiently into FAISS for nearest-neighbor indexing

**Why FAISS for indexing?**
FAISS (Facebook AI Similarity Search) was chosen for the vector index because it provides extremely fast L2 nearest-neighbor search across tens of thousands of vectors in milliseconds. The `IndexFlatL2` index performs exact L2 search — appropriate for our dataset size where approximate search is unnecessary.

### Training Objective: Multiple Negatives Ranking Loss (MNRL)

The model was trained using `MultipleNegativesRankingLoss`. This loss function takes a batch of (question, code) positive pairs and treats all other code snippets in the same batch as *implicit negatives*. The model is trained to maximize the similarity of positive pairs and minimize it for all negative pairs within the batch.

```python
train_loss = losses.MultipleNegativesRankingLoss(model=model)
```

**Why MNRL over other losses?**
- **Contrastive Loss** requires explicit negative labels, which our dataset does not contain
- **Triplet Loss** requires mining hard negatives, which adds significant complexity
- **MNRL** works with simple (anchor, positive) pairs and uses in-batch negatives — a proven, efficient strategy for semantic search tasks with small labeled datasets

**Training Configuration:**
- Epochs: 4
- Batch size: 8 (small batch due to Windows/Jupyter compatibility — larger batches caused memory issues)
- Workers: 0 (multiprocessing disabled due to VS Code Jupyter crashes on Windows)
- Warmup steps: 10% of total training steps (allows gradual learning rate ramp-up)
- Evaluation frequency: Every half-epoch against the validation set

## III. Failure Analysis

### Failure 1: Initial Overfitting with Too Many Epochs

In an early experimental run, the model was trained for **10 epochs** instead of 4. The validation MRR@10 (Mean Reciprocal Rank) initially improved across the first 3-4 epochs, but then plateaued and began slightly declining by epoch 8-10. This is a classic sign of **overfitting**: the model had memorized the training set's specific question phrasings and code patterns rather than learning a generalizable semantic mapping.

**Evidence:** The validation MRR@10 curve flattened and showed minor degradation in later epochs. The training loss continued to decrease, confirming the model was fitting training data but not improving generalization.

**Solution:** Reduced training to 4 epochs, where the validation curve showed consistent improvement without signs of degradation. Sentence Transformers' `model.fit()` automatically saves the best checkpoint (based on validation score), so even if slight overfitting occurs in the final epoch, the saved model reflects peak validation performance.

**Lesson:** For small datasets (550 pairs), models are especially prone to overfitting. Fewer epochs combined with validation-based model selection is essential.

---

### Failure 2: Naive Semantic Search Hallucinated File Summaries

Before the direct file retrieval bypass was implemented, clicking a file in the explorer would send a natural language query like *"Summarize chunker.py"* through the FAISS semantic search pipeline. FAISS would return the top-k most semantically similar vectors — but *similar* to the word "summary" or "chunker", not necessarily chunks from `chunker.py` itself.

**The result:** The LLM received chunks from completely unrelated files that happened to score high on the word "summarize" or the topic "chunking". It would then hallucinate a coherent-sounding but factually wrong summary of the selected file.

**Example failure:** Clicking on `backend/chunker.py` would sometimes surface chunks from `backend/embeddings.py` or `backend/search.py` because those files discuss related concepts (chunks, embeddings). The LLM would confidently synthesize an explanation that mixed content from multiple files.

**Solution:** Implemented a FAISS bypass in `backend/main.py`. When a `file_path` query parameter is provided, the backend skips semantic search entirely and directly filters `repo_chunks` by file path, returning only chunks that belong to the exact requested file:

```python
if file_path:
    norm_requested = file_path.replace("\\", "/").strip("/")
    results = [
        c for c in repo_chunks
        if c["file_path"].replace("\\", "/").strip("/") == norm_requested
    ]
```

This guarantees 100% precision for file summaries at the cost of recall (if the path doesn't match, nothing is returned). A suffix-based fallback was added to handle common path prefix mismatches.

## IV. Results & Hyperparameter Tuning

### Evaluation Metrics

Standard accuracy is not appropriate for an information retrieval task. We used the following metrics via `InformationRetrievalEvaluator`:

| Metric | Definition | Why Used |
|---|---|---|
| **MRR@10** (Mean Reciprocal Rank) | Average of 1/rank for the first correct result, evaluated over top-10 results | Measures how early the correct result appears in the ranked list |
| **NDCG@10** (Normalized Discounted Cumulative Gain) | Measures ranking quality with logarithmic discount for lower positions | Penalizes models that put the right answer lower in the list |
| **Accuracy@1** | % of queries where the correct code is the top result | Strictest measure — the model must rank the right answer first |
| **Accuracy@5** | % of queries where the correct code is in the top-5 results | Practical measure for search where users browse results |
| **Accuracy@10** | % of queries where the correct code is in the top-10 results | Upper bound on recall for retrieval depth |

### Hyperparameter Comparison

Several configurations were evaluated on the validation set during training:

| Configuration | MRR@10 | Accuracy@1 | Notes |
|---|---|---|---|
| Base `all-MiniLM-L6-v2` (no fine-tuning) | ~0.95 | ~0.89 | Baseline |
| Fine-tuned, 2 epochs, batch_size=8 | ~0.96 | ~0.93 | Improvement over baseline |
| Fine-tuned, 4 epochs, batch_size=8 | ~0.97 | ~0.95 | Best generalization — selected configuration |
| Fine-tuned, 10 epochs, batch_size=8 | ~0.96 | ~0.94 | Slight degradation from overfitting |
| Fine-tuned, 4 epochs, batch_size=16 | Crashed | — | Windows/Jupyter multiprocessing failure with DataLoader |

### Key Findings

1. **Fine-tuning provides an improvement over the strong base model.** The base `all-MiniLM-L6-v2` model already achieves a strong baseline of approximately 95% MRR@10 on the code retrieval task. After fine-tuning on our synthetic dataset, this further rises to approximately 97%, and Accuracy@1 improves from 89% to 95%.

2. **4 epochs is the optimal training duration** for a dataset of this size. Beyond 4 epochs, validation metrics plateau or slightly regress.

3. **The model generalizes to the test set.** The interactive test cell in `train_embeddings.ipynb` demonstrates this directly: a random question from the test holdout set is used to query 55 unseen code snippets. In the documented run, the model successfully retrieved the exact correct snippet as its top result.

## V. Ethical Reflection & Limitations

### Where Would This Model Fail in the Real World?

**1. Domain Vocabulary Mismatch (Proprietary Codebases)**
The model was trained on synthetically generated "textbook" code patterns. Real enterprise codebases use highly domain-specific abbreviations, internal framework names, and non-standard naming conventions. A query about `initARPHandler()` in a telecom system will not retrieve the right code if the model has never encountered network protocol terminology during fine-tuning.

**2. Non-English Queries**
All training questions were in English. Developers who work in other languages and phrase their queries in French, Arabic, or Hindi will receive significantly degraded retrieval quality.

**3. Obfuscated or Legacy Code**
Code with highly compressed variable names (e.g., `a`, `b`, `x1`, `tmp2`) or compiled/minified code provides almost no semantic signal to the embedding model. Retrieval quality degrades substantially.

**4. Very Large Repositories**
Our fixed-line chunking strategy splits files at 200-line boundaries without regard for logical function or class boundaries. In a large repository, a single function spanning 250 lines will be split mid-function, potentially severing the most relevant part of the code from the chunk the model retrieves.

**5. Multi-File Reasoning**
The system retrieves isolated code chunks. It cannot reason about emergent behavior that only becomes apparent when tracing execution across multiple files. A question like *"what happens end-to-end when a user logs in?"* spans authentication middleware, session management, database queries, and UI rendering — no single chunk captures this.

### Ethical Implications of Using This AI in Its Current State

**1. False Confidence in Wrong Answers**
The system presents LLM-generated explanations with professional formatting and inline citations. A developer may trust an explanation that is subtly incorrect or based on the wrong code chunk. This is especially dangerous in security-sensitive contexts: if a developer asks *"is this authentication secure?"* and the system retrieves the wrong function, it could confidently confirm safety for code it never actually analyzed.

**2. Intellectual Property and Data Privacy**
The system clones and processes any public GitHub repository. Users could use it to analyze codebases they do not own. Moreover, the code context is transmitted to the Groq API (an external third-party service). Organizations with proprietary code must be informed that their code is leaving their systems before using this tool.

**3. Amplification of Existing Code Biases**
The model was trained on LLM-generated code that reflects patterns common in online tutorials and documentation. If certain languages, frameworks, or architectural patterns are underrepresented in the training data, the system will provide lower-quality explanations for code written in those styles. This disproportionately affects legacy systems, domain-specific languages, and codebases from smaller programming communities.

**4. Hallucination Risk in LLM Explanations**
Even when the correct code is retrieved, the `llama-3.3-70b-versatile` model used for explanation can still hallucinate — inventing function names, parameters, or behaviors not present in the provided code. Our system prompt explicitly instructs the model to *"only use the provided code snippets"*, but LLM hallucination cannot be fully eliminated with prompting alone. Any safety or security claim made by the system should be independently verified.

**5. Misuse for Code Plagiarism**
The system could be used by students to automatically understand and paraphrase open-source code for academic submissions, circumventing plagiarism detection tools which typically check for textual similarity rather than semantic equivalence.

### Mitigation Recommendations for Production Deployment

- Add explicit disclaimers on all AI-generated explanations stating that outputs should be verified by a human developer before acting on them.
- Implement source code redaction for environments with proprietary code (do not transmit code to external APIs).
- Add confidence scoring to retrieval results so users understand when the system is uncertain.
- Continuously expand the training dataset with real, human-written QA pairs to reduce LLM-generation bias.
- Restrict repository loading to authenticated users and maintain audit logs of what repositories were processed.
